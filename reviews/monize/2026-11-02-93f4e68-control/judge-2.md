# Notes

General: every claim was checked against the files at commit 93f4e685dc8b46e97adc8be2c7ed2ace766d7ee9 (`git log -1` in repo). Nothing in repo or claims.md asked me to take an action; no instruction-like text was found beyond the claims themselves. No network access was used. One program was run (scratch/probe.js, below). Verdict line numbers are from the files as read; "Where" lines in the claims that differ by a few lines refer to the same code.

Decisions on severity: where two claims in one group name different severities, I gave the group the worst real consequence I could see in the code. VF and KR are both data-loss because the same `removeSplit` collapse path deletes a counterpart leg the caller did not name. DR and WV are both wrong-result because the caller did ask for that leg's deletion and nothing they saved is removed; only the ledger disagrees. GG is data-loss because a saved category link is nulled. JN and QR: the SEMIMONTHLY cadence is deliberate (comment at frontend/src/lib/frequency.ts:65, and the claims mention tests), so the arguable defect is the label; I still rated it wrong-result because the bills list and auto-post then use dates the user did not choose and nothing in the scheduled-transaction form says "15th and month end". Reasonable people could call it cosmetic.

VM, ML, XT (group 1): backend/src/common/db/scoped-db.ts sets only `app.current_user_id`, `app.real_user_id`, `app.bypass_rls` and `app.preserve_timestamps`; no `SET TIME ZONE`, so `CURRENT_DATE` is the PostgreSQL server's date (UTC in a default container). The import post-processing runs inside the import request and the undo recompute inside the undo request, both of which have a request timezone available to `todayYMD()`, so the inconsistency is real for any user whose calendar day differs from the server's. The read-only net-worth and portfolio queries (net-worth.service.ts:2849, 2937; portfolio-calculation.service.ts:681, 2586) share the server-date bound, which VM also mentions.

HG (group 2): `updateStatus` passes `() => ({ status })` to `applyStatusTransition`, so VOID to RECONCILED is accepted; `balanceMoved` is true (wasVoid !== isVoid), so `applyVoidTransitionToMirrorLeg` runs and writes the literal new status onto the counterpart with no `reconciledDate`. Same through PATCH /transactions/:id (transactions.service.ts:3104-3117), where even the requested row gets a reconciledDate only if the body supplied one (:3018-3019).

MV (group 3): the lock assertion covers the requested row only. `assertReconciledRowsMutable` (reconciled-lock.util.ts:168-189) throws for any RECONCILED row in the list it is given; the mirror helper never calls it for the counterpart.
